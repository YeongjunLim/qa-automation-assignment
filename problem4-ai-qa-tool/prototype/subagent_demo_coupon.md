# 실제 실행 기록 — tc-generator ↔ tc-critic 서브에이전트 데모

이 문서는 [.claude/agents/tc-generator.md](../../.claude/agents/tc-generator.md)와
[.claude/agents/tc-critic.md](../../.claude/agents/tc-critic.md)에 정의된 역할을, Claude Code의
`Agent` 도구로 **실제로 호출**해서 나온 원본 결과를 그대로 기록한 것이다 (요약·각색 없음). 새로 만든
커스텀 sub-agent 타입은 세션 재시작 없이는 즉시 인식되지 않아(`Agent type 'tc-generator' not found`),
`general-purpose` 타입에 위 두 파일의 역할 정의를 프롬프트로 그대로 주입해 실행했다 — 이 한계는
[README.md](../README.md)와 [PROCESS.md](../PROCESS.md)에도 명시했다.

입력 요구사항, 생성/검토 라운드는 [TestLedger 목업](testledger.html)의 "TC 설계·작성" 화면에 요약
반영되어 있다.

## 입력 요구사항 (쿠폰 적용 기능)

```
- 쿠폰은 발급(ISSUED) → 사용가능(AVAILABLE) → 사용완료(USED) 상태를 가진다. 발급 후 유효기간이
  지나면 AVAILABLE에서 EXPIRED로 전환된다.
- 이미 USED이거나 EXPIRED인 쿠폰은 다시 사용할 수 없다.
- 쿠폰마다 '최소 주문금액' 조건이 있다. 주문 금액이 최소 주문금액 미만이면 쿠폰을 적용할 수
  없다(정확히 같으면 적용 가능).
- 쿠폰 코드는 사용자가 직접 입력한다. 존재하지 않는 쿠폰 코드를 입력하면 에러를 반환한다.
- 한 주문에는 쿠폰을 최대 1개만 적용할 수 있다. 이미 쿠폰이 적용된 주문에 다른 쿠폰을 적용하려
  하면 거부된다.
```

## 1라운드 — tc-generator 초안 (16건)

상태전이 6건 · 경계값분석 3건 · 동등분할 2건 · 결정테이블 5건. 전체 표는 대화 로그 참고,
핵심은 각 기법이 명시적으로 라벨링되고, 마지막에 "동등분할을 quantity류 값에 중복 적용하지
않은 이유"와 "페어와이즈를 적용하지 않은 이유"를 스스로 밝혔다는 점이다.

## 1라운드 — tc-critic 검토 결과: **반려 — 7건 수정 필요**

1. TC-DT-04, TC-DT-05 — "입력" 컬럼 누락으로 재현 불가능
2. TC-EP-02 ↔ TC-DT-01 — 사실상 동일 케이스가 다른 기법 이름으로 중복
3. TC-EP-01 — 예상결과("정상 진행")가 모호해 통과/실패 판정 불가
4. 유효기간 만료 경계값(BVA) 커버리지 누락 — 최소주문금액에만 BVA 적용됨
5. "USED 쿠폰 + 유효기간 경과" 시 EXPIRED로 오전환되지 않아야 함을 검증하는 불허 전이 케이스 누락
6. TC-ST-01 — 요구사항에 없는 절차("활성화 처리")를 임의로 가정
7. 결정테이블의 조건 우선순위가 요구사항에 근거 없이 암묵적으로 설정됨

## 2라운드 — tc-generator 수정본

7건을 모두 반영: 입력 컬럼 보완, EP-02/EP-03로 무효 클래스 분리, 모호한 EP-01 제거, BVA-04/05
(유효기간 경계) 추가, ST-06(USED 오전환 방지) 추가, ST-01에 가정 명시, 결정테이블에 우선순위
각주 추가.

## 2라운드 — tc-critic 재검토: **반려 — 6건 수정 필요** (4건 해소 · 2건 신규 발견 · 1건 미해소)

- ✅ 해소: 입력 컬럼 누락, 유효기간 BVA 누락, USED 오전환 방지 누락, 우선순위 미표시
- ❌ 미해소: EP-02 ↔ DT-01 중복이 이름만 바뀌었을 뿐 실질적으로 안 풀림
- 🆕 신규 발견: TC-ST-01의 사전조건("발급 완료")과 입력("발급 요청 실행")이 논리적으로 모순됨 —
  가정을 끼워 넣는 과정에서 생긴 새로운 결함
- 🆕 신규 발견: TC-BVA-02와 TC-DT-05가 완전히 같은 입력조합을 검증하는 과잉 중복

## 이 데모가 보여주는 것

1라운드에서 7건, 2라운드에서도 6건이 반려됐고 그중 2건은 "수정하다가 새로 생긴 결함"이었다.
**한 번에 "승인"이 나지 않았다는 것 자체가 이 도구의 존재 이유를 증명한다** — AI가 생성한 테스트
케이스는 단 한 번의 검토로 신뢰할 수 없고, 검토자 역할이 반복적으로 필요하며, 최종 확정은 반드시
사람이 해야 한다는 설계 원칙([README.md](../README.md) "신뢰성 확보 방안" 참고)이 그대로
증명된 셈이다.
