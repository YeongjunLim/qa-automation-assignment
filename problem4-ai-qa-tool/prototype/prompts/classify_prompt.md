# Flaky 실패 분류 프롬프트 템플릿

`flaky_triage.py`의 `build_prompt()`가 아래 템플릿에 실제 실패 데이터를 채워 LLM에 전달한다.
출력은 반드시 아래 JSON 스키마를 따르도록 강제한다 (파싱 실패 시 규칙 기반 폴백으로 전환).

```
당신은 시니어 QA 엔지니어이자 테스트 자동화 전문가입니다.
아래는 CI에서 실패한 테스트 1건에 대한 정보입니다. 이 실패의 근본 원인을 아래 5개 카테고리 중
하나로 분류하고, 반드시 지정된 JSON 형식으로만 답변하세요. 설명이나 추가 텍스트는 포함하지 마세요.

[카테고리 정의]
- ENV_ISSUE: 테스트 인프라/환경 문제 (네트워크 순단, 인프라 리소스 부족, 외부 의존 서비스 장애 등)
- TIMING_ISSUE: 대기 전략 부족으로 인한 타이밍 문제 (고정 sleep, 비동기 처리 완료 전 조회 등)
- TEST_CODE_DEFECT: 테스트 코드 자체의 결함 (취약한 셀렉터, 잘못된 assertion, 테스트 격리 부족 등)
- DATA_ISSUE: 테스트 데이터/픽스처 문제 (다른 테스트와 데이터 충돌, 픽스처 미초기화 등)
- REAL_BUG: 테스트가 실제 제품 결함을 정확히 잡아낸 경우

[테스트 이름]
<<test_name>>

[테스트 코드 스니펫]
<<test_code_snippet>>

[실패 스택트레이스 / 에러 메시지]
<<stack_trace>>

[최근 <<history_length>>회 실행 이력] (true=성공, false=실패, 시간순)
<<recent_history>>

[재시도 시 통과 여부]
<<retry_passed>>

[출력 JSON 스키마]
{
  "category": "ENV_ISSUE | TIMING_ISSUE | TEST_CODE_DEFECT | DATA_ISSUE | REAL_BUG",
  "confidence": 0.0~1.0 사이 숫자,
  "evidence": "판단 근거를 스택트레이스/이력의 구체적 내용을 인용해 1~2문장으로",
  "suggested_owner": "QA | DEV | INFRA",
  "suggested_fix": "구체적인 다음 조치 1~2문장",
  "draft_comment": "Slack/Jira에 바로 올릴 수 있는 한국어 코멘트 초안 (2~4문장)"
}
```

## 설계 의도

- **카테고리를 5개로 한정**한 이유: 너무 세분화하면 모델이 매번 다른 표현을 만들어내 라우팅 로직(if/else)이 불안정해진다. 문제1에서 정의한 Flaky 트리아지 분류 체계와도 맞춰 팀 내 용어를 통일했다.
- **evidence를 필수로 요구**한 이유: "왜 그렇게 판단했는지"가 없으면 사람이 결과를 검증할 수 없고, 결국 다시 로그를 처음부터 읽어야 해 도구의 존재 의미가 없어진다.
- **draft_comment까지 생성**하는 이유: 분류만 하고 끝나면 사람이 다시 문장을 써야 하는 추가 작업이 남는다. "바로 게시만 하면 되는 초안"까지 만들어야 실제 시간 절약 효과가 난다 (단, 게시는 반드시 사람이 승인).
- **치환 자리표시자로 `{}` 대신 `<<...>>`를 쓴 이유**: 템플릿 안에 출력 예시로 JSON 스키마(`{ "category": ... }`)가 그대로 들어 있어, `str.format()`으로 치환하면 스키마의 중괄호까지 자리표시자로 오인되어 깨진다. `build_prompt()`는 `<<placeholder>>`를 단순 문자열 치환(`str.replace`)으로 처리해 이 문제를 피한다.
