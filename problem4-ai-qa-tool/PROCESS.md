# 문제4 — 함께 풀어나간 과정

> 최종 답변은 [README.md](README.md)에 있습니다. 이 문서는 최종 아이디어(TestLedger)에 도달하기까지
> 여러 대안을 검토하고 좁혀나간 전체 과정을 기록합니다 — 이 문제는 특히 아이디어 자체가 여러 번
> 바뀌었기 때문에, 그 궤적을 남기는 것 자체가 의미 있다고 판단했습니다.

## 1. Claude의 1차 제안 — Flaky Triage Assistant

Claude가 먼저 "실패 로그 자동 분류" 도구를 제안하고 `flaky_triage.py`를 구현·실행 검증했다 (5개
카테고리, 규칙기반 폴백 + LLM 모드). 이 과정에서 프롬프트 템플릿의 실제 버그(JSON 스키마 예시의
중괄호가 `str.format()`과 충돌)를 발견해 수정했다.

## 2. 지원자가 실제 채용공고(JD)를 제시 — 재검토의 계기

지원자가 이 포지션의 JD 전문을 공유. 분석 결과:
- 우대사항에 "AI/LLM을 활용한 테스트 자동화(**테스트 생성**, **자가 치유 스크립트** 등)"가 명시돼
  있는데, 과제 PDF의 3개 예시 중 Claude가 고른 "실패 로그 분류"만 여기 빠져 있었음
- 반면 "Flakiness 등 품질 지표 관리", "해결 방향까지 제안", "내부 도구 개발"이라는 JD 문구는
  Flaky Triage와 정확히 부합
- Claude가 1차로 제안한 절충안: 기존 프로토타입은 유지하고, README에 "확장 로드맵"(1단계 분류 →
  2단계 Self-healing/TC생성)을 추가하는 방향

## 3. 지원자의 실무 경험 — "코드 검증 자동화, 우리 회사도 아직 안 하고 있다"

지원자가 실제로 회사에서 AI로 테스트 스크립트를 짜지만 "돌려보고 에러나면 고치는" 반응적 방식에
머물러 있다고 밝힘. 이 언급을 계기로 Claude가 문제4의 **제목**("AI 생성 코드 검증 자동화")을
다시 읽고, 본문 예시보다 제목이 더 좁고 구체적인 걸 가리킨다고 판단 — "AI가 생성한 코드/테스트가
맞는지 검증"하는 도구로 전면 전환 제안. [문제3](../problem3-e2e-refactor)에서 도출한 5개 문제를
정적 검사 룰셋으로, 문제3의 원본 코드를 데모 입력으로 쓰자는 구체안까지 나옴.

## 4. 지원자의 더 큰 통찰 — "Self-healing보다 거대한 시스템이 필요하다" (1차)

지원자가 실무에서 겪은 실패 원인 대부분이 "다른 테스트케이스 수행에 따른 영향"(테스트 간 의존성)
이었다며, 점 단위 self-healing보다 "요구사항부터 프로젝트 끝까지 안 끊기고 이어지는 시스템"이
필요하다는 통찰을 제시. Claude가 "추적성(traceability)"을 축으로 한 요구사항→TC→코드→실행→
회고 파이프라인을 그려 보였으나, **지원자가 스스로 "이건 실무엔 필요하지만 지금 문제 범위와는
결이 다르다"고 정리** — 범위를 좁히기로 함.

## 5. 방향 전환 — "테스트케이스 설계 및 작성"

지원자가 코드 검증 자동화도, 거대 시스템도 아닌 **"테스트케이스 설계·작성"** 도구를 원한다고 결정.
[문제2](../problem2-bmart-stock-api)에서 직접 적용한 블랙박스 설계기법(상태전이/경계값/동등분할/
결정테이블)을 AI가 보조하는 도구로 설계 — 문제2와 문제4가 자연스럽게 연결되는 지점을 찾음.

## 6. Self-healing 요구 + Claude Team/Sub-agent/Agent Team 개념 정리

지원자가 "작성한 TC를 검토하고 스스로 고치는" self-healing 요소가 꼭 필요하다며, Claude Team/
Sub-agent/Agent Team의 차이를 물음. Claude가 정리: Claude Team은 사람이 여러 명 쓰는 구독
플랜(자동화 아키텍처와 무관), Sub-agent는 부모-자식 관계의 일시적 위임, Agent Team은 여러
독립 에이전트의 수평적 협업. 지원자의 목적엔 "Generator↔Critic 역할 분리"가 핵심이라는 데
합의했고, Claude가 처음엔 "CI 배포 가능성"을 이유로 API 직접 호출 방식을 권했다.

## 7. 지원자의 정정 — "문제4에 CI 얘기는 없다"

지원자가 과제 원문엔 CI 배포 요구사항이 없다고 지적 — Claude가 스스로 추가한 가정이었음을 인정.
이후 지원자가 "실제로 Claude Code의 sub-agent 기능을 써본 것"을 보여주는 게 목적이라고 명확히
밝힘 (`Claude Team vs Sub-agent vs API` 비교에서 Sub-agent 실사용 쪽으로 확정).

## 8. 실제 실행 — 커스텀 sub-agent의 한계를 직접 발견

`.claude/agents/tc-generator.md`, `tc-critic.md`를 만들고 실제로 `Agent` 도구로 호출을 시도했으나
**세션 재시작 없이는 커스텀 타입이 인식되지 않는다는 걸 실행해보고 확인** (`Agent type
'tc-generator' not found`). 정직하게 이 한계를 밝히고, 이미 등록된 `general-purpose` 타입에 두
정의의 역할을 프롬프트로 그대로 주입해 우회 실행.

지원자가 문제2 도메인(재고) 재사용을 원하지 않아 **쿠폰 적용 기능**을 새 예시로 정함. 실제로
Generator→Critic 루프를 2라운드 실행: 1차 초안(16건) → Critic 반려(7건) → 수정본 → Critic
재검토 → **반려(6건, 그중 2건은 수정 과정에서 새로 생긴 결함)**. 원본 기록은
[`prototype/subagent_demo_coupon.md`](prototype/subagent_demo_coupon.md).

지원자가 이 시점에 "역할을 설계/작성/검토 3단계로 더 쪼개면 어떨까"를 제안했다가, 아래 9번에서
방향이 다시 바뀌며 이 3단계 세분화 논의는 최종안에는 반영되지 않았다.

## 9. 지원자의 재통합 — "거대한 시스템" 재소환 (2차, 이번엔 범위가 다름)

지원자가 다시 한번 더 큰 그림을 제시: **서비스 등록 → TC 설계/작성 → CI 실행 → 실패 분석(기존
Flaky Triage 파이프라인) → 수정 코드 예시까지 주는 자동 수정 제안 → 유지보수**를 하나의 도구로
묶고, 목적은 **"테스트케이스 자산화"**. 4번의 "요구사항부터 끝까지"보다 스코프가 명확했고(테스트
자산의 생애주기로 한정), Claude가 "1단계(Flaky Triage, 이미 구현) + 2단계(TC 설계/작성 +
Self-healing 코드 제안, 로드맵)"라는 2번의 절충안과 정확히 다시 만난다는 걸 확인 — 이번엔 방금
실제로 실행한 Generator/Critic 데모를 "2단계가 실제로 동작한다"는 증거로 그대로 재활용할 수 있게
됨.

## 10. 프로토타입 형식 확정

지원자가 확인 사항 두 가지를 정리: ① 이 확장 부분(수정 코드 제안, 서비스 등록/자산 관리)은 실제로
동작하는 코드까지는 필요 없고 **설계상 결함만 없으면 됨** ② 프로토타입은 **정적 HTML 목업 하나**로,
GitHub에 파일로 올려 다운받아 열어보면 충분함.

## 11. TestLedger 목업 제작

Claude가 대시보드/TC 설계·작성/CI 실패 분석/수정 제안/자산 이력 5화면 구조를 제안하고, **이미
실제로 만들어낸 데이터**(쿠폰 기능 Generator/Critic 데모, `flaky_triage.py`의 4건 분류 결과,
문제3의 `Thread.sleep` 사례)를 그대로 샘플로 재사용해 Artifact로 발행. 지원자 피드백으로 각 화면의
큰 제목(h1)이 사이드바 메뉴명과 일치하도록 전체 수정 (예: "수집기→정규화→분류→라우터"였던 제목을
"CI 실패 분석"으로, 세부 설명은 작은 라벨로 이동).

## 정리

이 문제는 결과적으로 "실패 로그 분류 → 코드 검증 → 요구사항 전체 시스템 → TC 설계/작성 →
Self-healing → 테스트 자산화 플랫폼"까지 총 6번 방향이 바뀌었다. 마지막에 수렴한 "테스트케이스
자산화"라는 목적이, 그 이전 모든 대안(분류/검증/생성/치유)을 배제하지 않고 **각각을 자산 생애주기의
한 단계로 재배치**했다는 점에서, 이전 논의가 버려진 게 아니라 전부 최종안에 흡수됐다.
