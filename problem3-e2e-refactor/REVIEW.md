# 문제3. E2E 자동화 코드 리뷰

## 원본 코드

```kotlin
@Test
fun testOrderFlow() {
    val shopItem = device.wait(Until.findObject(By.textContains("치킨")), 5000)
    shopItem.click()
    val menuItem = device.wait(Until.findObject(By.textContains("후라이드")), 3000)
    menuItem.click()
    val orderBtn = device.wait(Until.findObject(By.textContains("주문하기")), 3000)
    orderBtn.click()
    val payBtn = device.wait(Until.findObject(By.textContains("결제")), 3000)
    payBtn.click()
    Thread.sleep(5000)
    val statusText = device.wait(Until.findObject(By.textContains("접수 대기")), 3000)
    Assert.assertNotNull(statusText)
}
```

## 발견한 문제점

핵심 문제 5가지로 압축했다. (다른 후보 — 클릭 가능 여부 미확인, 팝업 미고려, 결제 성공/실패 분기, 테스트 데이터 정리 — 도 논의했지만, 대부분의 경우 실제로 문제가 되는 빈도가 낮거나 범위가 애매해서 핵심 5가지에서는 제외했다. 근거는 [PROCESS.md](PROCESS.md) 참고.)

| # | 문제 | 관점 | 왜 문제인가 |
|---|---|---|---|
| 1 | `By.textContains("치킨")`, `"후라이드"`, `"주문하기"`, `"결제"`, `"접수 대기"` — 부분일치 셀렉터가 테스트 본문에 하드코딩 | 안정성 + 유지보수성 | 프로모션 배너·마케팅 카피에 같은 문자열이 포함되면 의도치 않은 다른 요소를 클릭할 수 있고(안정성), UI 문구가 바뀌면 이 문자열을 쓰는 곳을 전부 찾아 고쳐야 한다(유지보수성). Page Object가 없어 셀렉터가 테스트 코드 전역에 흩어져 있다는 게 근본 원인이다. |
| 2 | 매직 넘버(`3000`, `5000`)로 대기시간을 지정, 값도 제각각 | 유지보수성 | 왜 3000이고 왜 5000인지 근거가 없고 한 곳에 모여 있지도 않다. CI가 느려져 타임아웃 정책을 전체적으로 조정해야 할 때 일일이 찾아 바꿔야 한다. |
| 3 | `Thread.sleep(5000)` 고정 대기 | 안정성 | 결제 처리(서버 응답)가 5초보다 오래 걸리면 그대로 실패하고, 1초 만에 끝나도 무조건 5초를 낭비한다. 이 테스트에서 가장 확실한 Flaky 원인이자 실행 시간 낭비의 원인. |
| 4 | 이 테스트가 검증하는 요구사항/시나리오를 알려주는 주석이나 Given-When-Then 구조가 없음 | 유지보수성(추적성) | "치킨 주문 성공" 케이스라는 건 코드를 끝까지 읽어야 짐작 가능하다. 어떤 백로그·요구사항에 대응하는 테스트인지 남아있지 않으면, 나중에 유지보수하는 사람이 이 테스트를 지워도 되는지, 다른 케이스와 뭐가 다른지 판단할 근거가 없다. |
| 5 | `Assert.assertNotNull(statusText)`만으로 검증 | 신뢰성 | "접수 대기"라는 텍스트를 가진 View를 찾았다는 것만 확인할 뿐, 정확한 문구인지(부분일치라 다른 문구에도 매치 가능), 실제로 화면에 보이는지(`isVisibleToUser`)는 검증하지 않는다. |

## 리팩토링 방향 요약

1. **Page Object Model** 적용 → 화면(Home/Menu/Order/Payment/OrderStatus)마다 클래스 분리, 셀렉터를 한 곳으로 응집 (문제 1)
2. **대기시간 상수화** → `Timeouts` 객체 하나에 모아 정책을 한 곳에서 관리 (문제 2)
3. **`Thread.sleep` 전면 제거** → 폴링 기반 명시적 대기(`UiWaitUtils`)로 대체 (문제 3)
4. **Given-When-Then + 요구사항 주석** → 테스트 함수에 이 케이스가 검증하는 시나리오를 명시 (문제 4)
5. **검증 강화** → 상태 텍스트의 정확한 문구 + `isVisibleToUser`까지 확인 (문제 5)

리팩토링된 코드: [`src/`](src) 디렉터리 참고. 위 5가지 외에, 클릭 가능 상태까지 확인하는 `waitForClickable`이나 결제 성공/실패를 구분하는 `waitForAny` 같은 방어적 장치도 코드에 추가로 넣었다 — 이건 "원본의 결함"이라기보다 "더 견고하게 만들 수 있는 지점"이라 핵심 5개 문제 목록과는 별도로 다뤘다.

## 이 테스트가 CI에서 간헐적으로 실패한다면(Flaky) — 원인 추적 순서

1단계: **재현성부터 확인** — 실패가 특정 커밋 이후 100% 재현되는지(→ 실제 회귀), 아니면 간헐적인지(→ 진짜 flaky) 먼저 구분한다. 최근 N회 실행의 pass/fail 이력을 확인한다.

2단계: **실패 시점(어느 Page Object 단계)을 확인** — 리팩토링 후에는 각 단계가 분리되어 있으므로 스택트레이스만으로 "메뉴 선택 단계"인지 "결제 단계"인지 "상태 확인 단계"인지 즉시 특정할 수 있다.

3단계: **아티팩트 확인** — `TestWatcher`가 남긴 실패 시점 스크린샷과 view hierarchy 덤프를 확인해, 예상치 못한 팝업/다이얼로그가 떠 있었는지, 아니면 정상 화면인데 셀렉터만 못 찾았는지 눈으로 확인한다.

4단계: **타이밍 vs 로직 구분**
   - 스크린샷상 화면은 정상인데 셀렉터가 못 찾았다면 → 대기시간 부족(서버 응답 지연, 애니메이션 지연) 의심 → 실패 시점의 백엔드 응답 시간 로그와 대조
   - 화면 자체가 다르거나 팝업이 떠 있었다면 → 테스트 코드가 처리하지 못한 새로운 UI 요소(신규 배포된 팝업 등) 의심 → 최근 배포 이력과 대조

5단계: **환경 요인 확인** — 특정 디바이스/에뮬레이터, 특정 시간대(피크 타임 서버 부하로 응답 지연), 특정 테스트 실행 순서(이전 테스트가 남긴 데이터/상태 오염)에서만 발생하는지 CI 매트릭스를 교차 분석한다.

6단계: **분류 및 조치**
   - 테스트 코드 결함(대기 전략 미흡, 셀렉터 취약) → 즉시 수정
   - 실제 제품 버그(간헐적으로 결제 응답이 늦거나 상태 전이가 누락) → 개발자에게 이관, 테스트는 정확한 재현 조건을 기재해 티켓 생성
   - 원인 불명 시 → 우선 quarantine 처리(격리)하고 재발 빈도를 계속 관찰하며 로그 계측을 추가해 다음 발생을 기다린다 (문제1의 Flaky 대응 정책과 동일한 프로세스).
