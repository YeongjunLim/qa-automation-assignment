# 문제3. E2E 자동화 코드 리뷰

## 원본 코드

```kotlin
@Test
fun testOrderFlow() {
    val shopItem = device.wait(Until.findObject(By.textContains("치킨")), 5000)
    shopItem.click()
    val menuItem = device.wait(Until.findObject(By.textContains("후라이드")), 3000)
    menuItem.click()
    val orderBtn = device.wait(Until.findObject(By.textContains("주문하기")), 3000)
    orderBtn.click()
    val payBtn = device.wait(Until.findObject(By.textContains("결제")), 3000)
    payBtn.click()
    Thread.sleep(5000)
    val statusText = device.wait(Until.findObject(By.textContains("접수 대기")), 3000)
    Assert.assertNotNull(statusText)
}
```

## 발견한 문제점

### 1. 안정성 (Stability) — 실제 환경에서 간헐적으로 깨지는 지점

| # | 문제 | 왜 문제인가 |
|---|---|---|
| 1-1 | `Thread.sleep(5000)` 고정 대기 | 결제 처리(서버 응답)가 5초보다 오래 걸리면 그대로 실패하고, 반대로 1초 만에 끝나도 무조건 5초를 낭비한다. Flaky의 가장 흔한 원인이자 전체 스위트 실행 시간을 갉아먹는 원인. |
| 1-2 | `By.textContains("치킨")` 등 텍스트 기반 셀렉터 | 프로모션 배너, 다른 카테고리명, 마케팅 문구("치킨은 옳다" 등)에 동일 문자열이 포함되면 **의도치 않은 다른 요소를 클릭**할 수 있다. 텍스트는 A/B 테스트·카피 변경에도 취약해 기능은 안 바뀌었는데 테스트만 깨지는 원인이 된다. |
| 1-3 | `findObject` 결과를 바로 `.click()` | 요소가 화면에 "존재"하는 것과 "클릭 가능(활성화, 애니메이션 완료, 다른 뷰에 가려지지 않음)"한 것은 다르다. 존재 확인만 하고 클릭하면 터치가 씹히거나 잘못된 좌표를 클릭할 수 있다. |
| 1-4 | 팝업/다이얼로그 미고려 | 앱 업데이트 안내, 권한 요청, 이벤트 팝업 등 예기치 못한 오버레이가 뜨면 이후 모든 `findObject`가 타임아웃으로 실패한다. 실제 운영 환경에서 이런 팝업은 상시 발생 가능하다. |
| 1-5 | 사전 상태(precondition) 가정 | 앱이 이미 홈 화면에, 로그인된 상태로, "치킨" 카테고리가 노출되어 있다는 것을 암묵적으로 가정한다. 테스트가 어떤 화면에서 시작하는지 코드로 보장하지 않는다. |

### 2. 유지보수성 (Maintainability)

| # | 문제 | 왜 문제인가 |
|---|---|---|
| 2-1 | Page Object 부재, 셀렉터가 테스트 본문에 하드코딩 | "주문하기" 버튼 텍스트가 바뀌면 이 문자열을 쓰는 **모든 테스트 파일**을 찾아 고쳐야 한다. UI 변경 1건이 테스트 코드 N군데 수정으로 이어진다. |
| 2-2 | 매직 넘버(3000, 5000)가 테스트 곳곳에 흩어짐 | 타임아웃 정책을 바꾸려면(예: CI 서버가 느려서 전체적으로 여유를 둬야 할 때) 모든 곳을 일일이 찾아 바꿔야 한다. |
| 2-3 | 단계별 책임 구분 없는 단일 메서드 | "메뉴 선택"과 "주문/결제"와 "상태 확인"이 한 함수에 뒤섞여 있어, 실패 시 어느 화면 로직이 문제인지 테스트 코드만 보고는 파악하기 어렵고, 재사용도 불가능하다(다른 테스트에서 "장바구니에 담기까지"만 재사용 못 함). |
| 2-4 | 실패 시 디버깅 정보 없음 | 실패해도 스크린샷/현재 화면 계층(view hierarchy) 덤프가 남지 않아, CI 로그만 보고는 "왜" 실패했는지 재현 없이는 알 수 없다. |

### 3. 신뢰성 (Reliability) — 통과해도 못 믿을 수 있는 지점

| # | 문제 | 왜 문제인가 |
|---|---|---|
| 3-1 | `Assert.assertNotNull(statusText)` | "접수 대기"라는 텍스트를 가진 View를 찾았다는 것만 검증할 뿐, 그 View가 **화면에 보이는지(visible)**, **정확한 문구인지**(부분 문자열 포함이라 "접수 대기중입니다"뿐 아니라 엉뚱한 "접수 대기 이력 없음" 같은 문구에도 매치될 수 있음), **활성화된 진짜 주문 상태 배지인지**는 전혀 검증하지 않는다. False positive(실제로는 실패인데 테스트는 통과)의 원인. |
| 3-2 | 주문 성공/실패 갈림 처리 없음 | 결제 실패(잔액 부족, 네트워크 오류 등) 시 나타나는 에러 다이얼로그를 구분하지 않아, 결제가 실패했는데도 다음 `findObject`가 우연히 다른 텍스트에 매치되면 테스트가 "성공"으로 잘못 종료될 수 있다. |
| 3-3 | 테스트 격리/정리(cleanup) 없음 | 테스트가 실제로 주문을 생성하는데, 이 주문을 취소/정리하는 로직이 없다. 반복 실행 시 테스트 계정에 주문 데이터가 계속 쌓여 이후 테스트(주문 내역 조회 등)에 영향을 줄 수 있다. |

## 리팩토링 방향 요약

1. **Page Object Model** 적용 → 화면(Home/Menu/Order/Payment/OrderStatus)마다 클래스 분리, 셀렉터를 한 곳으로 응집
2. **`Thread.sleep` 전면 제거** → 폴링 기반 명시적 대기(`UiWaitUtils`)로 대체하고, "요소 존재"가 아니라 "클릭 가능/텍스트 일치까지" 조건화
3. **셀렉터 강화** → 가능하면 `resourceId` 우선 사용(코드 내 주석에 실제 앱 리소스 ID를 가정했음을 명시), 텍스트는 `textContains` 대신 `text`(정확히 일치) 우선
4. **검증 강화** → 상태 텍스트의 정확한 문구 + `isVisibleToUser` + (있다면) 주문번호 등 부가 데이터까지 검증
5. **실패 시 아티팩트 수집** → `TestWatcher`로 실패 시 스크린샷 자동 캡처
6. **단계 로깅** → 각 Page Object 메서드 진입/이탈 시 로그를 남겨 실패 지점을 즉시 특정 가능하게 함

## 이 테스트가 CI에서 간헐적으로 실패한다면(Flaky) — 원인 추적 순서

1단계: **재현성부터 확인** — 실패가 특정 커밋 이후 100% 재현되는지(→ 실제 회귀), 아니면 간헐적인지(→ 진짜 flaky) 먼저 구분한다. 최근 N회 실행의 pass/fail 이력을 확인한다.

2단계: **실패 시점(어느 Page Object 단계)을 확인** — 리팩토링 후에는 각 단계가 분리되어 있으므로 스택트레이스만으로 "메뉴 선택 단계"인지 "결제 단계"인지 "상태 확인 단계"인지 즉시 특정할 수 있다.

3단계: **아티팩트 확인** — `TestWatcher`가 남긴 실패 시점 스크린샷과 view hierarchy 덤프를 확인해, 예상치 못한 팝업/다이얼로그가 떠 있었는지, 아니면 정상 화면인데 셀렉터만 못 찾았는지 눈으로 확인한다.

4단계: **타이밍 vs 로직 구분**
   - 스크린샷상 화면은 정상인데 셀렉터가 못 찾았다면 → 대기시간 부족(서버 응답 지연, 애니메이션 지연) 의심 → 실패 시점의 백엔드 응답 시간 로그와 대조
   - 화면 자체가 다르거나 팝업이 떠 있었다면 → 테스트 코드가 처리하지 못한 새로운 UI 요소(신규 배포된 팝업 등) 의심 → 최근 배포 이력과 대조

5단계: **환경 요인 확인** — 특정 디바이스/에뮬레이터, 특정 시간대(피크 타임 서버 부하로 응답 지연), 특정 테스트 실행 순서(이전 테스트가 남긴 데이터/상태 오염)에서만 발생하는지 CI 매트릭스를 교차 분석한다.

6단계: **분류 및 조치**
   - 테스트 코드 결함(대기 전략 미흡, 셀렉터 취약) → 즉시 수정
   - 실제 제품 버그(간헐적으로 결제 응답이 늦거나 상태 전이가 누락) → 개발자에게 이관, 테스트는 정확한 재현 조건을 기재해 티켓 생성
   - 원인 불명 시 → 우선 quarantine 처리(격리)하고 재발 빈도를 계속 관찰하며 로그 계측을 추가해 다음 발생을 기다린다 (문제1의 Flaky 대응 정책과 동일한 프로세스).
