## 1. Claude의 1차 구현 설명

Claude가 먼저 완성해둔 결과물(Mock 서버, pytest 15개 + 동시성 3개, 실제 실행해서 18개 전부 통과 확인)을 어떤 판단으로 만들었는지 설명했다 — Python 선택 이유, `test_client()` 대신 진짜 소켓 서버를 쓴 이유, 동시성을 3개로 나눠 검증한 이유 등.

## 2. 지원자의 방향 전환 — "테스트케이스 설계"가 이 문제의 진짜 포인트

지원자가 결과물 자체는 인정하되, **이 문제가 평가하려는 건 Mock 서버 구현력이 아니라 테스트케이스 설계 역량**이라고 판단. Mock 서버·pytest 인프라는 그대로 두고, "배경/재고 처리 규칙 표"를 지원자가 직접 다시 설계해보고 싶다고 요청.

## 3. 설계기법 어필 방향 확정

지원자가 "재고 있음/없음으로 상태전이를 쓴다던지"처럼 **정식 블랙박스 테스트 설계기법(ISTQB류)을 명시적으로 적용했다는 걸 어필하고 싶다**는 방향을 제시. 이후 Claude와 함께 기법을 하나씩 순서대로 적용:

1. **상태 전이 테스트**: 재고 상태(IN_STOCK/SOLD_OUT)와 주문 상태(COMPLETED/CANCELLED)를 별도 다이어그램 두 개로 분리. "재고 부족으로 거절된 주문"은 애초에 Order 엔티티가 생성되지 않으므로 상태 전이가 아니라는 것도 함께 정리.
2. **경계값 분석**: quantity의 하한(고정 경계 1)과 상한(재고값 자체가 경계인 **동적 경계**)을 구분. `quantity = stock`(경계값)이 상태 전이의 `IN_STOCK→SOLD_OUT` 트리거와 같은 지점이라는 것도 짚음 — 두 기법이 같은 취약점을 다른 각도에서 가리킨다는 걸 명시.
3. **동등 분할**: 지원자가 먼저 "명세에 다단계 구간(여유/품절임박/재고없음 같은)이 없으니 quantity엔 EP가 딱히 필요 없지 않냐"고 지적 → Claude가 동의하고, 대신 **순서가 없는 범주형 값(productId, orderId)** 에 EP를 적용하는 걸로 방향 수정. quantity에 EP를 적용하려 한 것 자체가 기법 오용이었다는 걸 지원자가 먼저 짚어낸 것.
4. **결정 테이블**: '재고 처리 규칙' 표의 "운영자 수정 중 주문 발생 시 처리 순서 정의 필요"를 조건 2개(처리 순서 × 재고 충분 여부)의 조합 4가지(R1~R4)로 풀었다. R3/R4에서 "운영자 수정 = 절대값 덮어쓰기"라는 기존 설계의 함의(주문 결과와 무관하게 최종값은 항상 운영자 지정값)가 드러난 것도 이 과정에서 발견.

## 5. ID 부여 + 문서/코드 분리 + 실제 구현

지원자 요청: ①설계서에 테스트케이스 ID 부여 ②테스트케이스 명세를 설계서와 별도 파일로 분리 ③이를 바탕으로 실제 자동화 스크립트까지 완성 ④과제 요구 카테고리(정상/재고복구/품절전환)와 동시성 시나리오가 몇 번 TC인지 확인.

- TC-01~TC-25로 코드에 등장하는 순서대로 ID 부여 (기법별로 번호를 나누지 않고 순차 부여 — 테스트가 늘어나도 기존 ID가 안 흔들리도록)
- [TEST_DESIGN.md](TEST_DESIGN.md)(기법·근거) / [TEST_CASES.md](TEST_CASES.md)(입력값·예상결과 상세)로 문서 분리
- 설계 단계에서 식별됐지만 코드에 없던 7개(TC-16~TC-22)를 실제로 구현: 기존 파일에 3개(경계값 하한 미만, 경계값 상한 바로 위, 운영자 재입고 상태전이), 신규 파일 `tests/test_admin_update_ordering.py`에 결정 테이블 4개(R1~R4)
- 전체 25개를 실제 pytest로 실행해 **전부 통과** 확인 (venv 생성 → 설치 → 실행 → venv 삭제)

## 6. 재검토(2026-09-07) — 함수명/문서화 리팩토링

지원자가 코드를 다시 보고, 함수명(`def test_...`)이 그 자체로 설명이 되려다 보니 너무 길다고 지적. 개선 방향으로 ①적절히 짧은 함수명 ②주석으로 어떤 테스트케이스인지 명시 ③Given-When-Then 구조로 유지보수성을 높이는 것을 제안.

- 함수명을 `test_tc{번호}_{짧은 요약}` 규칙으로 전부 변경 (예: `test_get_stock_returns_current_quantity` → `test_tc01_get_current_stock`) — 이미 부여해둔 TC-ID를 함수명에도 그대로 노출해, 테스트 목록만 봐도 TEST_CASES.md와 바로 대조 가능하게 함
- 각 함수 docstring에 `TC-ID | 요구사항 카테고리 | 적용기법` 한 줄 + `Given/When/Then` 3줄을 표준 포맷으로 추가
- 함수 본문에도 `# Given`/`# When`/`# Then` 주석으로 동일 흐름을 표시
- README.md·TEST_DESIGN.md·TEST_CASES.md에 있던 기존 함수명 참조도 전부 새 이름으로 일괄 치환
- 25개 전체를 다시 pytest로 실행해 **전부 통과** 재확인
