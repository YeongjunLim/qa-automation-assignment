## 1. Claude의 1차 시도 — 제약 조건에서 출발

Claude가 먼저 "개발자 2명 / 2주 / 자동화 0건"이라는 제약을 뽑아 "모든 걸 자동화하면 오픈을 못 지킨다"는 전제를 세우고, 판단 기준(반복빈도/회귀파급력/검증안정성) → 피라미드(Unit 70/API 25/E2E 5%, 추상적 비율) → ROI 체크리스트 → CI/CD 단계 → Flaky 정책 순으로 답을 만들어 설명했다.

## 2. 지원자의 첫 반박 — "실시간 주문 현황이 정확히 뭔데?"

지원자가 지적: 고객 앱엔 이미 "배달현황"이 있는데, "실시간 주문 현황"이라는 신규 화면이 굳이 고객용일 이유가 있나? 이름도 다르고, 사장님이 주문을 관리하는 화면(배민 사장님 앱)일 가능성이 높다고 제안.

→ Claude가 동의하고, 이 재정의가 답변 전체(actor, 사용 기기, 자동화 우선순위)에 영향을 준다는 걸 확인. "이미 존재하는 사장님 앱에 새 화면 하나 추가"로 범위를 확정(지원자 확인, 시나리오의 "새로운 화면을 추가"라는 표현 근거).

## 3. 화면 정의 구체화

- **"서비스 = 자동화 0건"이 앱 전체를 가리키는가?** — 지원자: "서비스"라는 단어를 특정 기능 하나에 쓰지 않으니 앱 전체가 맞다. → Claude가 반영: 이번 자동화 자산이 "이 화면 전용"이 아니라 앱의 **첫 자동화 인프라**가 된다는 함의 추가.
- **상태값 정의** — 지원자가 미확인/조리중/배달대기중/배달중/배달완료 + 리뷰 노출까지 직접 정의. "일간으로 보여줘야 할 것 같다"는 지적에서 자정 경계 케이스가 새로 도출됨.
- **일간 뷰 기준** — 지원자: 매장 운영시간 기준, 주문 시각 기준, 24시간 매장은 datetime 자정 기준. → Claude가 여기서 파생되는 구체적 테스트 케이스(경계값 테스트, 23:50 주문/00:20 완료 케이스 등)를 도출하고, 이 로직이 API/데이터 레벨에서 검증하기 좋은 고ROI 후보임을 지적.
- **실시간 갱신 메커니즘(웹소켓 vs 폴링)** — 지원자가 프로토콜을 특정하지 않고 요구사항 레벨로 서술하자고 제안. 실제 구현 방식은 개발팀과 협의해 정할 사항이므로, 전략 문서 단계에서 미리 못박기보다 "상태 전이가 지연 없이 정확히 반영되는가"라는 요구사항 자체에 집중하는 게 더 실용적이라는 판단.

## 4. 리소스/환경 전제 합의

지원자가 먼저 문제 제기: "테스트 케이스 수, 인원 같은 것도 전제해야 하지 않냐." 이어서 하나씩 확정:
- QA 인원 1명(지원자 본인) — 지원자 확정
- 실기기 존재, 인프라 셋업 불필요 — 지원자 확정, 단 "2주 내내 스크립트만 쓰는 건 아니지 않냐"고 반박

## 5. 일정 재설계 — "요구사항 리뷰는 이미 끝났다"는 재해석

지원자: 시나리오가 "이번 주부터 개발 시작"이라 했으니, 요구사항/백로그 검토는 이미 그 전주에 끝났다고 봐야 한다. → 이 재해석 덕분에 Day1의 "요구사항 리뷰"가 빠지고, 스크립팅 가용일이 늘어남. 대신 "테스트 케이스 설계(전주 초안 → Day1 오전 확정)"와 "스크립트 작성(Day1 오후부터)"은 구분해서 일정에 반영.

이 과정에서 Claude가 **Contract-First 전략**(API 계약만 먼저 합의하고 Mock으로 먼저 테스트 작성, 나중에 실서버로 전환)을 제안했고, 이게 [문제2](../problem2-bmart-stock-api)에서 과제 제약 때문에 어쩔 수 없이 썼던 Mock 서버 방식과 동일한 실무 패턴임을 확인 — 두 문제가 하나의 이야기로 연결됨.

최종 일정(Day1~10)과 스크립팅 캐파(UI 6~7 / API 20~25 / E2E 2)를 이 논의로 확정.

## 6. 레이어 배분과 CI/CD 단계 정교화

자동화/수동 판단표와 레이어 배분(UI/API/E2E)을 정리한 뒤, 지원자가 "CI/CD에 넣는다면 UI, API가 들어가는 거지?"라고 질문. Claude가 여기서 "PR 단계에 뭘 넣을지"를 감이 아니라 **CI/CD 게이팅의 기본 원칙**으로 답했다.

- **PR을 막는 테스트의 자격 조건은 "빠르고 결정적인가"다.** 그렇지 않은 테스트를 PR 필수 체크에 넣으면, 스테이징 인프라가 잠깐 느려지거나 장애가 날 때마다 그 순간 코드와 무관한 모든 개발자의 머지가 함께 막히는 부작용이 생긴다.
- 이 기준을 적용하면 **UI 컴포넌트 테스트는 항상 fake로 격리돼 있어 예외 없이 PR 단계**에 들어가지만, API/통합 테스트는 균일하지 않다 — 같은 "API 테스트"라도 **지금 Mock을 보고 있는지, 실제 스테이징을 보고 있는지**에 따라 외부 의존성 유무가 갈리기 때문이다. Mock 대상은 UI 테스트와 동일하게 PR 단계에 넣고, 실제 스테이징을 호출하는 것만 merge-이후 단계로 분리했다.
- 이걸 4단계 파이프라인으로 구체화: **PR 단계**(UI 전체 + Mock 기반 API, 매 push 수분 내) → **merge-이후**(스테이징 전환된 API + E2E, 실인프라라 PR 흐름과 분리) → **Nightly**(전체 회귀 + 자정 경계처럼 시각 의존적인 저빈도 케이스) → **배포 직전 게이트**(핵심 E2E 스모크 1개 + API 헬스체크).
- 이 구조는 5번에서 짠 개발 일정(Day1~2 Mock 먼저 → Day3~5 실서버로 순차 전환)과 그대로 맞물린다. 스프린트 초반엔 API 테스트 전부가 Mock 대상이라 몽땅 PR 단계에서 돌다가, 스테이징 전환이 끝나는 것부터 순차적으로 merge-이후 단계로 옮겨가는 흐름이 된다 — 파이프라인 설계와 개발 일정이 서로 다른 논리에서 나온 게 아니라 같은 전제(Contract-First)에서 자연스럽게 파생됐다는 뜻이다.

지원자 동의.

## 7. Flaky 원인 — 지원자가 4대 요인 직접 제시

지원자가 비동기/타이밍, 테스트 간 의존성, 외부 환경/데이터 변수, 자원 부족 4가지를 먼저 제시. Claude가 이걸 [문제4](../problem4-ai-qa-tool) Flaky Triage Assistant의 5개 카테고리와 매핑하고, 우리 시나리오(실시간성, 시간 기반 로직)에 대입해 구체적 위험과 대응을 도출.

## 8. ROI — 지원자의 정교화가 가장 컸던 부분

Claude가 처음 제시한 3축(회귀파급력×발생빈도/작성비용) 공식에 지원자가 여러 개선을 제기:
1. "발생빈도가 꼭 버그 발견 확률만은 아니다, 정기 점검 자체도 Return" → Frequency를 "회귀감시가치"로 재정의
2. "사람이 준비하기 번거로운 걸 자동화해서 아끼는 시간도 Return" → **수동대체가치** 축 신설
3. "Cost를 나누는 것보다 전부 망대특성(높을수록 좋음)으로 통일해서 곱하는 게 낫지 않냐" → Cost를 효율(4-Cost)로 뒤집어 곱셈으로 통일
4. "다음 배포에 사라질 기능이면 자동화 투자가 아깝다" → **수명(Longevity)** 축 신설

최종적으로 5축(파급력×감시가치×수동대체가치×수명×효율) 공식을 만들고, 기존 후보들에 재적용해 결론이 뒤집히지 않음을 검증 — 오히려 "왜 동시성/일간뷰가 최우선인지"가 "사람이 재현 불가능"이라는 더 설득력 있는 근거로 뒷받침됨.
