# 문제1 — 함께 풀어나간 과정

> 최종 답변은 [README.md](README.md)에 있습니다. 이 문서는 그 답을 만들기까지의 사고 과정과
> 사용자와의 논의 내용을 기록합니다.

## 1. 문제를 그대로 풀지 않고, 제약 조건부터 뽑아냈다

시나리오를 읽고 가장 먼저 한 일은 "이 시나리오가 일반적인 자동화 전략 질문과 뭐가 다른가"를 찾는 것이었다.

- 개발자 **2명**, 오픈까지 **2주** → 인력·시간이 빠듯함
- 기존 자동화 테스트 **0건** → 인프라부터 새로 구축해야 함
- 신규 기능이라 스프린트 중에도 요구사항/UI가 흔들릴 가능성이 높음

이 세 조건을 조합하면 "이번 스프린트에 전부 자동화하려 하면 오히려 오픈 일정을 위협한다"는 결론이 나온다. 이 문장을 답변의 전제로 먼저 세우고, 이후 모든 판단(무엇을 자동화할지, 피라미드 배분, 파이프라인 단계)을 이 전제에서 역산했다.

## 2. "무엇을 자동화할지"를 감이 아니라 판단 기준으로 만들었다

단순히 항목을 나열하면 근거가 약해 보이기 때문에, 판단 기준 3가지를 먼저 정의했다.

1. 반복 실행 빈도 (매 빌드마다 확인이 필요한가)
2. 회귀 파급력 (실패 시 매출/신뢰도 직결 여부)
3. 검증 안정성 (결과가 결정적인가, 사람 판단이 필요한 감성 영역인가)

이 기준을 적용해 "API 계약 테스트·최초 렌더링·핵심 해피패스"는 자동화, "실시간성 체감 품질·디자인·저빈도 엣지케이스"는 수동으로 분류했다. 추가로 "이번에 자동화하지 않으면 다음 스프린트부터 계속 수동 반복해야 하는가?"라는 한 줄 기준을 넣었는데, 이건 QA 실무에서 가장 자주 쓰이는 실용적 잣대라고 판단해서 포함했다.

## 3. 테스트 피라미드는 역삼각형이 아니라 정삭 피라미드로

자동화 자산이 0건인 상태에서 E2E부터 두껍게 쌓으면 유지보수 비용이 감당 안 된다고 판단해, `Unit 70% / API 25% / E2E 5%`로 배분했다. "왜 API에 가장 많이 투자하는가"의 근거는 화면 특성과 연결했다 — "실시간 주문 현황"의 본질은 API/실시간 채널이 정확한 상태값을 내려주는지이지, UI 자체는 부차적이라는 논리다.

## 4. ROI는 계산식 하나 + 실무 체크리스트로

ROI를 숫자로 딱 떨어지게 계산할 수는 없다고 보고, 개념 공식(`(회귀 탐지 가치 × 실행 빈도) / (작성+유지보수 비용)`) 하나와, 실무에서 바로 쓸 수 있는 5개 체크리스트(실행 빈도/신호 대 잡음비/유지보수 비용/수동 대체 시간/장애 임팩트)로 풀었다. 특히 "깨지는 빈도 대비 잡아내는 버그 수(신호 대 잡음비)"를 넣은 이유는, Flaky해서 계속 재시도만 하고 있는 테스트는 실질적으로 마이너스 ROI라는 걸 놓치기 쉬운 포인트라고 봤기 때문이다.

## 5. 파이프라인 단계는 "속도 vs 커버리지" 트레이드오프로

PR 단계엔 5분 내로 끝나는 것만(Unit + API 계약), E2E는 merge 이후/nightly로 미뤘다. 개발자가 2명뿐인 체제에서 PR마다 E2E까지 돌리면 대기시간이 개발 속도 자체를 깎아먹는다는, 시나리오의 "개발자 2명" 제약에서 역산한 결정이다.

## 6. Flaky 정책은 "숨기지 않는 재시도"로

재시도를 무조건 허용하면 flaky를 감추는 도구가 되어버리므로, 재시도는 허용하되 **재시도로 통과한 케이스를 별도로 카운트**하고, 통과율이 낮은 테스트는 자동으로 quarantine 처리하는 규칙을 넣었다. 원인 분류 체계(환경/타이밍/테스트결함/실제버그)는 이후 **문제4의 AI 트리아지 도구 아이디어**로 그대로 이어지도록 의도적으로 설계했다 — 문제1~4가 하나의 이야기로 연결되게 하려는 의도.

## 사용자와의 논의

- 사용자가 "어떻게 문제를 풀었는지 설명해달라"고 요청 → 위 1~6 순서로 사고 과정을 구두 설명함
- 사용자가 세부 방향(ROI 정량화, 배민 조직 구조 반영 등)에 대한 추가 조정 여부를 아직 확정하지 않음 → 필요 시 이 섹션에 후속 논의 추가 예정
