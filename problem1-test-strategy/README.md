# 문제1. 테스트 자동화 전략 설계

## 시나리오 요약
- 신규 기능: "실시간 주문 현황" 화면
- 개발자 2명, 개발 기간 2주 (오픈까지 2주)
- 기존 자동화 테스트 0건 (그린필드 상황)

이 조건에서 가장 중요한 제약은 **시간**이다. 2주 안에 기능 개발 + 자동화 인프라 구축 + 테스트 작성을 모두 끝내야 하므로, "모든 걸 자동화한다"는 접근은 오히려 오픈 일정을 위협한다. 따라서 전략의 축은 **"오픈 전까지는 회귀 위험이 큰 지점만 얇고 확실하게 자동화하고, 나머지는 수동 탐색적 테스트로 커버한 뒤 오픈 이후 스프린트에서 자동화 자산을 넓혀간다"**로 잡았다.

## 1-1. 자동화 전략 수립

### 무엇을 자동화하고, 무엇을 수동으로 남길 것인가

판단 기준은 아래 3가지를 곱한 값(자동화 필요도)으로 본다.

| 기준 | 질문 |
|---|---|
| ① 반복 실행 빈도 | 이 케이스는 매 빌드/매 배포마다 반복 확인이 필요한가? |
| ② 회귀 파급력 | 실패했을 때 주문/결제처럼 매출·신뢰도에 직결되는가? |
| ③ 검증 안정성 | 결과가 결정적(deterministic)인가, 아니면 실시간성/디자인 감성처럼 사람 판단이 필요한가? |

**자동화 대상 (①②가 높고 ③이 명확한 것)**
- "실시간 주문 현황" 화면이 의존하는 **API 응답 스키마/상태값 계약 테스트** (주문 상태: 접수/조리중/배달중/완료 등 상태 전이가 명세대로 오는지)
- 화면 진입 시 **최초 데이터 렌더링**이 정상 동작하는지 (주문 리스트, 상태 배지 노출)
- 상태 변경 이벤트(WebSocket/폴링) 수신 시 **화면이 갱신되는지**의 핵심 해피패스 1~2개
- 기존 화면(주문내역, 홈)과의 **연동 지점 회귀** — 새 화면 진입/이탈이 다른 화면을 깨뜨리지 않는지

**수동으로 남기는 대상**
- **실시간성 체감 품질**: 실제 갱신 지연(예: 3초 이내 반영)처럼 타이밍 감각이 필요한 항목은 초기엔 수동 + 로그 기반 확인
- **디자인/애니메이션/UX 톤**: 배지 색상, 상태 전환 애니메이션 등 시각적 요소는 자동화 ROI가 낮음
- **저빈도 예외 조합** (네트워크 끊김 중 화면 전환, 알림 권한 거부 등 극단적 엣지케이스) — 오픈 초기엔 탐색적 테스트로 커버, 실제 이슈 재현 시에만 회귀 테스트로 승격
- **신규 기능이라 요구사항이 아직 흔들리는 부분**: 개발 2주차에 UI가 계속 바뀔 가능성이 높은 화면은, 자동화를 먼저 만들면 유지보수 비용만 커진다. 요구사항이 안정화된 후 자동화하는 게 ROI가 높다.

> 핵심 판단 기준 한 줄: **"이번 스프린트에 자동화하지 않으면, 다음 스프린트부터 매번 수동으로 반복해야 하는가?"** 가 아니오이면 지금은 수동으로 두고 백로그에 남긴다.

### 테스트 피라미드 관점의 레이어별 배분

2주라는 제약 + 자동화 자산이 전무하다는 점을 고려하면, **API 레이어에 가장 크게 투자**하고 E2E는 최소한의 스모크만 두는 역삼각형이 아닌 정삭 피라미드를 지향한다.

```
        E2E (5%)         ─ 오픈 전 필수 시나리오 1~2개 (주문 화면 진입 → 상태 표시 → 상세 이동)
      ────────────────
     API/통합 (25%)      ─ 주문 상태 API 계약 테스트, 상태 전이(전이 규칙) 테스트,
    ──────────────────    실시간 채널(WS/폴링) payload 검증, 인증/권한, 에러 응답
   ──────────────────────
  Unit/컴포넌트 (70%)     ─ 상태 매핑 로직(백엔드), 상태 배지/타이머 표시 로직(프론트 컴포넌트 단위)
```

- **Unit/컴포넌트 70%**: 개발자가 기능 구현과 동시에 작성. QA가 강제하기보다 "상태값 → 화면 라벨/색상 매핑" 같은 순수 로직에 대한 테스트를 페어로 리뷰하며 채워 넣는다. 개발자 2명 체제에서 QA가 모든 걸 직접 짤 수 없으므로, 여기는 **개발자 주도 + QA 리뷰**로 배분한다.
- **API/통합 25%**: QA가 가장 집중해야 할 지점. "실시간 주문 현황"은 결국 API/실시간 채널이 정확한 상태를 내려주는지가 핵심이므로, 여기에 시간을 가장 많이 쓴다.
- **E2E 5%**: Playwright/Appium 등으로 "가장 중요한 사용자 여정 1~2개"만 오픈 전에 만든다. E2E는 느리고 깨지기 쉬우므로 신규 화면 전체를 커버하려 하지 않는다.

### 자동화 투자 대비 효과(ROI) 판단 기준

ROI는 `(예상 회귀 탐지 가치 × 실행 빈도) / (최초 작성 비용 + 유지보수 비용)` 로 개념화하고, 실무에서는 아래 체크리스트로 근사한다.

1. **실행 빈도**: CI에서 매 PR마다 도는가, 릴리즈 때만 도는가 → 빈도가 높을수록 ROI ↑
2. **깨지는 빈도 대비 잡아내는 버그 수 (신호 대 잡음비)**: Flaky해서 계속 재시도/무시하게 되는 테스트는 ROI가 마이너스
3. **작성/유지보수 비용**: UI 요소가 자주 바뀌는 화면(이번처럼 2주차에도 UI가 흔들릴 화면)은 초기 자동화 비용이 실제 가치보다 큼
4. **수동 테스트 대체 시간**: 이 테스트 하나가 매번 QA 10분을 절약해주는가, 아니면 1분짜리 확인을 자동화에 1시간 들이는가
5. **장애 임팩트**: 실패 시 매출/고객 신뢰에 미치는 영향이 큰 영역(결제, 재고, 주문 상태)은 유지보수 비용이 다소 높아도 투자

이번 스프린트에서는 "주문 상태 API 계약"과 "핵심 해피패스 E2E 1개"가 위 기준에서 압도적으로 ROI가 높다고 판단해 최우선 자동화 대상으로 잡았다.

## 1-2. 파이프라인 통합

### CI/CD 단계별 실행 설계

| 단계 | 트리거 | 실행 테스트 | 목적 | 목표 소요시간 |
|---|---|---|---|---|
| PR 생성/업데이트 | `git push` to PR | Unit + 컴포넌트 테스트, API 계약 테스트(Mock 서버 기준) | 빠른 피드백, 머지 전 회귀 차단 | ~5분 |
| main 머지 후 (Merge Queue / post-merge) | merge to main | API 통합 테스트(스테이징 연동), 핵심 E2E 스모크 1~2개 | 실제 연동 환경에서의 회귀 확인 | ~10~15분 |
| 야간/정기 배치 (Nightly) | cron (예: 매일 새벽) | 전체 E2E 회귀 스위트, 저빈도 엣지케이스 | 넓은 커버리지, PR 흐름을 막지 않음 | 제한 없음 (30분~1시간) |
| 배포 직전 (스테이징 → 프로덕션) | 배포 파이프라인 gate | 스모크 테스트(로그인, 주문 조회, 신규 화면 진입) | 배포 승인의 최종 게이트 | ~3분 |

- PR 단계는 **빠르고 결정적인 테스트만** 배치해 머지 속도를 지키고, 느리거나 외부 의존성이 있는 테스트는 뒤 단계로 미룬다.
- E2E는 PR 단계에 넣지 않는다 — 개발 2명 체제에서 PR마다 E2E까지 돌리면 대기시간이 길어져 오히려 자동화가 개발 속도를 해친다.

### Flaky 테스트 대응 정책

1. **격리(Quarantine)**
   - Flaky로 의심되는 테스트는 즉시 `@Flaky`/`quarantine` 태그를 달아 **머지를 막는 필수(Required) 체크에서 제외**하고, 별도의 "격리 스위트"로 계속 실행은 시킨다 (신호는 계속 수집하되 사람을 막지 않음).
   - 격리된 테스트는 대시보드에 노출해 방치되지 않도록 SLA(예: 2주 내 원인 규명)를 둔다.

2. **재시도(Retry) 정책**
   - 재시도는 "숨기기"가 아니라 "신호와 잡음 구분"용으로만 제한적으로 사용한다.
   - CI 레벨에서 실패 시 최대 1~2회 자동 재시도를 허용하되, **재시도로 통과한 케이스는 별도로 카운트/로깅**해서 "재시도 후 통과율"을 추적한다. 이 수치가 계속 높은 테스트는 근본 원인 분석 대상으로 자동 승격한다.
   - 같은 테스트가 최근 N번 실행 중 M번 이상 재시도로 통과했다면 자동으로 quarantine 처리하는 규칙을 둔다.

3. **원인 분석(Root Cause Triage) 프로세스**
   - 1차: 실패 로그·스크린샷·네트워크 로그·재시도 시 통과 여부를 확인해 아래로 분류
     - 환경 이슈(테스트 데이터/인프라) / 타이밍(대기 전략 부족) / 테스트 코드 결함 / 실제 제품 버그
   - 2차: 분류 결과에 따라 소유자 지정 — 테스트 코드 결함/타이밍이면 QA가 즉시 수정, 실제 버그면 개발자에게 티켓 전달
   - 최근 실행 이력(pass/fail matrix)을 누적해 "특정 시간대(피크타임 배치 등)에만 실패"처럼 패턴을 찾는다.
   - (문제4에서 제안하는 AI 기반 실패 로그 자동 분류 도구가 바로 이 1차 분류 단계를 가속화하기 위한 아이디어이다.)

4. **재발 방지**
   - Flaky 원인이 "고정 대기시간(Thread.sleep)"이었던 사례는 조직 차원의 안티패턴으로 문서화하고, 코드 리뷰 체크리스트에 반영한다 (문제3 리팩토링 사례 참고).
