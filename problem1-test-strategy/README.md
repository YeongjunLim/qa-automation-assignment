# 문제1. 테스트 자동화 전략 설계

## 0. 시작하기 전에 — "실시간 주문 현황"이 정확히 뭔지부터 정의

과제 시나리오만 보면 이 화면이 고객용인지 사장님용인지 명시돼 있지 않다. 하지만 두 가지 단서로 볼 때 **배민 사장님 앱에 새로 추가되는, 식당 사장님이 들어오는 주문을 실시간으로 관리하는 화면**으로 정의했다.

- 고객 앱에는 이미 "배달현황"(배달 진행 트래킹)이 있다. 이름이 다르고("주문 현황" vs "배달현황"), 이미 있는 기능을 "신규로 추가"할 이유가 약하다.
- "주문 현황"이라는 표현 자체가 사장님이 들어오는 주문을 접수/조리/배달 단계로 관리하는 용어에 더 가깝다.

이 정의를 바탕으로 화면과 리소스 조건을 아래와 같이 구체화했다.

### 화면 정의
- **상태값 5단계**: 미확인 → 조리중 → 배달대기중 → 배달중 → 배달완료 (+ 배달완료 후 리뷰가 달리면 화면에 노출)
- **일간(daily) 뷰**: 매장 운영시간 기준으로 그룹핑한다. 심야 영업(예: 18시~익일 3시) 매장은 새벽 주문도 "전날" 영업일로 묶이고, 24시간 운영 매장은 datetime 자정을 기준으로 나뉜다. 기준은 항상 **주문이 들어온 시각**이며, 배달 완료 시각이 자정을 넘겨도 날짜는 바뀌지 않는다.
- **연동되는 화면**: 기존 사장님 앱에 이미 있는 홈/네비게이션에서 진입하는 신규 화면이다.

### 리소스/환경 전제
| 전제                                                  | 근거                                                            |
| --------------------------------------------------- | ------------------------------------------------------------- |
| 이 앱(사장님 앱) 전체가 자동화 테스트 0건                           | 시나리오가 "이 **서비스**에는 자동화 테스트가 전혀 없다"고 표현 — 화면 하나를 "서비스"라 부르지 않음 |
| 기존 화면(로그인, 네비게이션 등)은 안정적으로 동작 중                     | "새로운 화면을 **추가**하는" 스프린트이므로                                    |
| QA는 1인(지원자 본인)이 이 화면을 전담                            | 개인 과제 성격상 가장 현실적인 가정                                          |
| 회사 차원의 CI/CD 파이프라인은 이미 존재, 이번엔 "테스트 실행 스테이지"만 신규 추가 | 서비스를 이미 배포하고 있는 회사이므로                                         |
| 실기기(태블릿)는 이미 확보되어 있어 별도 인프라 셋업 불필요                  | QA 1인 체제에서 기기 조달까지 일정에 넣으면 2주가 더 빠듯해짐                         |
| 요구사항/백로그 검토는 "이번 주(개발 착수 주)" 이전에 이미 끝남              | 시나리오가 "개발자가 **이번 주부터** 개발 시작"이라 표현                            |

## 1-1. 자동화 전략 수립

### 실행 일정 — 자동화 캐파는 여기서 역산

QA가 요구사항 리뷰 부담 없이 2주를 시작하지만, 그렇다고 10일 내내 스크립트만 쓰는 것도 아니다. 개발이 기능을 순차적으로 완성해가는 동안 QA도 그에 맞춰 활동이 달라진다.

| 시점 | 활동 |
|---|---|
| Day1 오전 | 개발자와 API 계약 최종 확정 + 그 계약 기반 테스트 케이스 목록 확정 (전주에 초안이 있었다는 전제하에 반나절) |
| Day1 오후~Day2 | **Mock 서버 구축 → Mock 대상으로 자동화 스크립트 선(先)작성 시작** (Contract-First: 실제 백엔드가 없어도 합의된 계약으로 미리 테스트를 짬) |
| Day3~5 | 백엔드가 하나씩 완성되는 대로 Mock → 실제 스테이징으로 전환하며 스크립트 확장, 완성된 UI는 병행 수동 탐색적 테스트 |
| Day6~7 | E2E 시나리오 작성(Page Object), 기존 화면과의 연동 지점 회귀 확인 |
| Day8 | 버그 재검증, 자동화 스위트 flaky 안정화 |
| Day9 | 전체 회귀 스위트 실행 |
| Day10 | 최종 수동 스모크(알림음 등 자동화가 못 미치는 영역) + 오픈 게이트 체크 + 버퍼 |

실질적으로 스크립트 작성에 집중하는 기간은 약 7일(Day1 오후~Day7)이고, 이를 근거로 캐파를 **UI 6~7개 / API·통합 20~25개 / E2E 2개**로 잡았다.

> Contract-First 접근(Mock 먼저, 나중에 실서버로 전환)은 사실 [문제2](../problem2-bmart-stock-api)에서 "실제 서버가 없다"는 과제 제약 때문에 택한 방식과 동일하다. 과제의 제약이 실무에서 QA가 백엔드 완성을 기다리지 않고 먼저 테스트를 준비하는 전략과 그대로 맞아떨어진 셈이다.

### 자동화 vs 수동 판단 — ROI를 점수화

"이걸 자동화할까 말까"를 감으로 정하지 않기 위해, 투자(Investment=스크립트 작성 시간) 대비 회수(Return)를 5개 축으로 점수화했다.

```
점수 = 회귀파급력 × 회귀감시가치 × 수동대체가치 × 수명 × 효율
```

- **회귀파급력(1~3)**: 실패 시 사장님 업무/매출에 미치는 타격
- **회귀감시가치(1~3)**: 버그를 잡을 확률뿐 아니라, "매 배포마다 검증되고 있다"는 사실 자체가 주는 신뢰
- **수동대체가치(1~3)**: 사람이 직접 검증하려면 준비가 얼마나 번거로운가 (예: 특정 시각까지 기다려야 하거나, 동시 요청을 손으로 재현할 수 없는 경우 최고점)
- **수명(1~3)**: 이 기능이 다음 배포 이후에도 유지되는가. 일회성 기능이면 투자를 회수할 시간이 없으므로 낮게 잡는다 — 이번 "실시간 주문 현황"은 사장님 앱의 상시 기능이 될 것이므로 전반적으로 높게(3) 유지
- **효율(1~3)**: 작성 비용의 역수. UI(fake만 필요)=3, API(mock/스테이징 필요)=2, E2E(실기기+전체스택)=1

| 후보 | 파급력 | 감시가치 | 수동대체 | 수명 | 효율 | 결론 |
|---|---|---|---|---|---|---|
| 동시 다발 주문 처리 (API) | 3 | 2 | 3 (사람이 동시 요청 재현 불가) | 3 | 2 | 최우선 자동화 |
| 일간 뷰 경계 로직 (API) | 3 | 1 | 3 (자정까지 기다려야 검증 가능) | 3 | 3 | 최우선 자동화 |
| 상태 전이 5단계 (API) | 3 | 3 | 2 | 3 | 2 | 최우선 자동화 |
| 상태별 배지 렌더링 (UI) | 2 | 3 | 1 | 3 | 3 | 자동화 (비용이 낮아 거의 다 자동화해도 이득) |
| 앱 진입→리스트 노출 (E2E) | 3 | 1 | 1 | 3 | 1 | 자동화하되 최소 1개만 |
| 신규 주문 알림음(소리) | 2 | 1 | 1 | 3 | 1 | 수동 (디바이스 의존, 검증 자체가 불안정) |
| 배지 색상/애니메이션 디테일 | 1 | 1 | 1 | 3 | 1 | 수동 (감성 영역) |
| 태블릿 화면 꺼짐-켜짐 후 동기화 | 2 | 1 | 2 | 3 | 1 | 오픈 초기엔 수동 탐색적 테스트, 실제 이슈 재발 시 자동화로 승격 |

수명(Longevity) 축은 이번 사례에서는 대부분 3(상시 기능)으로 고정돼 순위를 크게 뒤집지는 않지만, "왜 초기부터 Page Object/Mock 인프라까지 갖춰 투자할 가치가 있는가"의 근거가 된다 — 앱 전체가 자동화 0건인 상태에서 이번에 만드는 자산이 사실상 **이 앱의 첫 자동화 인프라**가 되고, 그 인프라는 이번 화면이 사라지지 않는 한 계속 재사용되기 때문이다.

### 레이어별 배분 (UI / API / E2E)

과제가 요구한 대로 UI와 E2E를 구분했다. **UI 테스트는 화면을 앱 내부에서(in-process), 네트워크는 fake로 대체해 렌더링/상호작용만 검증**하는 컴포넌트 단위 테스트(예: Compose UI Test, Espresso)이고, **E2E는 실제 기기에서 앱 전체를 블랙박스로 조작**하며 여러 화면과 (가능하면) 실제 백엔드까지 통과하는 테스트(예: [문제3](../problem3-e2e-refactor)에서 쓴 UIAutomator)다. 둘은 "UI를 다루느냐"가 아니라 "격리냐 통합이냐"로 갈린다.

**UI (컴포넌트, 6~7개)**
1. 상태값 5종에 따른 배지 라벨·색상 렌더링
2. 리스트 정렬 로직 (미확인 건 최상단 등)
3. 상태 변경 버튼 tap 시 올바른 다음 상태 요청이 트리거되는지 (fake ViewModel로 호출 검증)
4. 배달완료 + 리뷰 존재 조건에서만 리뷰 아이콘 노출
5. 일간 뷰 날짜 전환 시 올바른 날짜로 조회 요청 트리거
6. 주문 0건일 때 빈 상태(empty state) 표시
7. API 실패 시 에러 문구/재시도 버튼 노출

**API/통합 (20~25개, 우선순위 순)**
1. 상태 전이 정상 흐름 5단계 각각 (5개)
2. 상태 전이 실패/역행 방지 케이스 — 예: 배달완료 상태를 조리중으로 되돌리는 시도 (4~5개)
3. 동시 다발 주문 처리 — [문제2](../problem2-bmart-stock-api)의 동시성 테스트와 동일한 패턴 (3개)
4. 일간 뷰 경계 로직 — 심야 운영 매장, 24시간 매장, 정확히 경계 시각 (3~4개)
5. 리뷰 노출 이벤트 반영 (2개)
6. 예외/에러 케이스 — 네트워크 실패, 잘못된 요청 등 (3개)

**E2E (2개)**
1. 앱 실행 → 오늘 주문 리스트가 정확히 노출 (핵심 해피패스, 기존 화면에서의 진입 포함)
2. 사장님이 상태 변경 버튼을 눌러 실제로 다음 상태로 전이 (실기기 기준)

**Unit** (QA 캐파에 포함하지 않음) — 일간 뷰 날짜 계산 함수, 상태 전이 규칙 함수 같은 순수 로직은 개발자가 작성하고 QA는 리뷰만 한다.

## 1-2. 파이프라인 통합

### CI/CD 단계별 실행

레이어 배분에서 "Mock이냐 실제 서버냐"가 자연스럽게 파이프라인 단계를 가르는 기준이 된다 — 외부 의존성이 없는 테스트는 빠르고 결정적이라 매 PR마다 돌려도 부담이 없고, 실제 인프라를 타는 테스트는 PR 흐름을 막지 않도록 뒤로 미룬다.

| 단계                 | 실행 테스트                                           | 이유                                 |
| ------------------ | ------------------------------------------------ | ---------------------------------- |
| **PR 단계** (매 push) | UI 컴포넌트 전체(6~7개) + API 중 **Mock 대상**             | 외부 의존성 없음 → 빠르고 결정적                |
| **merge 이후**       | API 중 **실제 스테이징 전환 완료분** + E2E 2개(실기기)           | 실인프라를 타 느리거나 덜 결정적일 수 있어 PR 흐름과 분리 |
| **Nightly**        | 전체 회귀(UI+API+E2E) + 일간 뷰 자정 경계처럼 시각 의존적인 저빈도 케이스 | 넓은 커버리지, 시간 제약 없음                  |
| **배포 직전 게이트**      | 핵심 E2E 1개(스모크) + API 헬스체크                        | 최종 승인                              |

스프린트 초반(Mock만 존재하는 시점)엔 API 테스트 전부가 PR 단계에서 돌다가, Day3~5에 걸쳐 스테이징 전환이 끝나는 것들부터 순차적으로 merge-이후 단계로 옮겨간다.

### Flaky 테스트 대응 정책

Flaky의 원인은 크게 4가지로 본다 — 이 분류는 [문제4](../problem4-ai-qa-tool)에서 제안한 Flaky Triage Assistant의 5개 카테고리(ENV_ISSUE/TIMING_ISSUE/TEST_CODE_DEFECT/DATA_ISSUE/REAL_BUG)와도 대응된다.

| 원인               | 우리 화면에서의 구체적 위험                                                                                             | 대응                                                                                                                                                                        |
| ---------------- | ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **비동기/타이밍 이슈**   | "실시간"이 핵심 요구사항이라 가장 취약. 상태 변경 후 화면 반영 대기, 동시성 검증 시 반영 시점 확인                                                 | `Thread.sleep` 금지, 폴링 기반 명시적 대기 사용 ([문제3](../problem3-e2e-refactor)에서 리팩토링한 패턴 재사용). 타이밍을 하드 어서션하지 않고 "정확한 최종 상태"만 검증 ([문제2](../problem2-bmart-stock-api) 동시성 테스트와 동일 원칙) |
| **테스트 간 의존성**    | 일간 뷰는 날짜별로 데이터가 누적되므로, 이전 테스트가 남긴 주문이 다음 테스트의 "오늘 목록"을 오염시킬 위험이 큼                                           | 테스트마다 격리된 테스트 매장 계정으로 실행 ([문제2](../problem2-bmart-stock-api)의 fixture 격리 원칙과 동일). 스테이징 전환 후에도 매장 단위 네임스페이스 격리 유지                                                          |
| **외부 환경/데이터 변수** | 이 기능은 "영업시간·자정 기준 날짜 그룹핑"이 핵심 로직이라 서버-클라이언트 시간 오차가 다른 기능보다 훨씬 치명적. 배차(라이더 매칭) 등 외부 시스템 연동 시 그쪽 불안정성이 전이될 위험 | 시간 의존 테스트는 시간을 고정(freeze)해 결정적으로 검증. 외부 시스템과의 경계는 Mock으로 끊고 계약 테스트로만 검증(그 시스템 자체 안정성은 해당 팀 책임)                                                                            |
| **자원 부족**        | CI/스테이징 인프라 부하 — QA 1인 체제에서 인프라 확장은 통제 밖                                                                    | 막기보다 "구분"에 집중 — 실패 로그에 리소스 사용량/응답 지연시간을 같이 남겨 로직 실패와 인프라 문제를 구분                                                                                                           |

**재시도 → 격리 → 원인분석** 순서로 대응한다. (원인과 무관하게 공통 적용)

**1) 재시도 — 1회로 제한**
재시도는 "일단 한 번 더 믿어본다"는 여지를 넉넉히 두지 않고 **딱 1회**로 제한한다. 이유는 순전히 비용 문제다 — 재시도 1건이 10초를 더 잡아먹는다면, 10건이면 100초, 100건이면 1000초가 그대로 스위트 실행 시간에 더해진다. 게다가 여러 환경(디바이스/OS 조합 등)에서 같은 스위트를 돌려야 한다면 이 비용은 조건 수만큼 배가된다. 그래서 재시도는 "구제"가 아니라 "이게 진짜 우연한 노이즈였는지 최소한으로 한 번 더 확인하는 신호"로만 쓴다. 재시도로 통과한 케이스는 별도로 카운트해 "재시도 후 통과율"을 추적한다.

**2) 격리 — 재시도 누적 3회를 CI 자동 quarantine 기준으로**
"즉시 원인을 고칠 수 없으면 격리한다"는 판단을 사람이 매번 내리지 않도록, CI에서 **같은 테스트가 재시도를 3회 누적하면 자동으로 quarantine** 처리한다 (예: 최근 실행에서 재시도가 발생한 횟수를 테스트별로 카운트해두고, 그 값이 3에 도달하는 순간 필수 체크에서 제외). 1~2회는 "우연"일 수 있어 그냥 지나가지만, 3회째부터는 우연으로 보기 어렵다는 경험적 임계값이다. 이렇게 자동화해두면 사람이 대시보드를 계속 들여다보지 않아도 된다.

여기서 놓치기 쉬운 지점은 **격리 대상 테스트가 앞뒤 테스트와 순서 의존성을 갖고 있을 수 있다는 것** — 예를 들어 이 테스트가 만들어주던 데이터를 다음 테스트가 전제로 깔고 있었다면, 그냥 빼기만 해서는 연쇄적으로 다른 테스트까지 깨진다. 그래서 격리할 때는 그 테스트가 앞뒤에 미치던 영향을 확인하고, 필요한 보정(예: 다음 테스트가 필요로 하던 사전 데이터를 별도로 채워주는 로직)까지 같이 처리한다.

**3) 원인분석 — 로그로 3갈래를 구분**
실행 실패 시 로그를 보고 (a) 스크립트 자체의 결함인지 (b) 실제 제품 버그(real bug)인지 (c) 테스트 실행 순서 때문에 생긴 문제인지를 가른다. 이건 곧 위 표의 4대 원인 중 어디에 해당하는지를 정하는 것과 같다.

- **비동기/타이밍 이슈는 예방 가능한 영역이었다.** 스크립트 작성 초기에 대기 전략(폴링 등)을 제대로 잡아두면, 이후엔 거의 재발하지 않았다.
- **반면 테스트 간 의존성이 실제로 가장 많이 겪은 결함 원인이었다.** 이상적으로는 매 테스트마다 완전히 새로운 격리 대상을 만드는 게 맞지만([문제2](../problem2-bmart-stock-api)의 fixture 격리 원칙 그대로), 그렇게 하면 실행 시간이 너무 늘어나 현실적으로는 일부를 공유·재사용하도록 절충하게 되고, **그 절충 지점에서 결함이 반복적으로 발생했다.** 즉 "완전 격리"와 "실행 시간"은 트레이드오프 관계이고, 이 화면의 자동화 설계도 이 트레이드오프에서 자유롭지 않다 — 완전 격리를 기본값으로 하되, 스위트가 커져 실행 시간이 부담되기 시작하면 이 절충 지점을 다시 검토해야 한다.

Frequency/ROI는 고정이 아니다. 지금은 "오픈 초기엔 수동"으로 둔 항목(예: 태블릿 화면 꺼짐-켜짐 후 동기화)도, 실제 운영 중 이슈가 반복되면 ROI 표의 회귀감시가치 점수가 올라가 자동화로 승격되어야 한다. 이 재산정의 근거 데이터를 쌓아주는 것이 바로 [문제4](../problem4-ai-qa-tool) Flaky Triage Assistant의 실패 이력 누적 기능이다.
